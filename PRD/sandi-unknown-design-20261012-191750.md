## Problem Statement

From your review, the current Mpower app feels mainly like a service directory, booking flow, and mood tracker. Your hypothesis is that people may also want a useful companion on an ordinary difficult day, when they are not looking to book an appointment.

Mira is an engineering experiment with a 2–3 focused Codex-day build window (about 16–24 Codex hours at 8 focused hours per day). Using the skill's rough 10–20× throughput estimate, that is about 160–480 human engineering hours (4–12 workweeks), not a calendar promise. Its demo should make the future clear enough to invite Mpower’s product and clinical team into the next conversation. It makes no treatment claim and is not a production launch.

## What Makes This Cool

Talk, Journal, and Actions stay as three clear surfaces available at any time. The following is an optional continuity example, not a required sequence:

1. A person writes or records a journal entry.
2. They select and edit one excerpt from that entry, then separately approve it for Talk. The full entry stays private in Journal.
3. Mira uses push-to-talk realtime voice and explicit orchestration functions in one FastAPI service to understand the immediate concern and offer two fixed actions.
4. The person chooses one action or declines; the Actions surface guides the fixed steps and records whether the person found it helpful.
5. The person separately chooses whether Mira may reuse their action rating as future context. They can open Talk at any time; if opted in and relevant, Mira names the rating source and lets them ignore it. Without opt-in, the rating stays out of Talk context.

The current app opens directly in Journal; there is no separate welcome screen. This is a default only; the person can move between tabs freely at any time. The demo shows continuity through permitted shared context, rather than three separate feature screens.

## Constraints

- Build window: 2–3 Codex days, about 16–24 focused Codex hours. The demo and core experience take priority; implementation code is disposable. The human-equivalent estimate is about 4–12 workweeks of engineering throughput, not calendar time.
- Target a normal React Native/Expo Android app for modern Android devices. The OnePlus is the primary physical QA/demo phone; record its Android version and investigate the exact model only if a compatibility issue appears. Use Expo Go for UI, Journal, and Actions iteration and a custom Expo development build for full realtime voice.
- Use OpenAI Realtime first; an OpenAI API key is available. Keep a small provider interface, but do not implement a second provider in this cycle unless the first experience is already excellent.
- Use real-time voice, text and voice journaling, consented context, tool calling, an action flow, and feedback where each improves the experience.
- Keep infrastructure small: single demo user, simple persistence, one running environment, one real provider implementation behind a small provider interface.
- Use synthetic demo entries. Show that voice is sent to the configured provider; Mira does not retain raw voice audio. Disclose the provider’s retention terms, and use synthetic data until those terms are checked.
- Talk uses push-to-talk: set `turn_detection: null`; on press send `input_audio_buffer.clear`, and if Mira is speaking send `response.cancel` plus `output_audio_buffer.clear`; stream while held; on release send `input_audio_buffer.commit` followed by `response.create`. Do not use VAD or automatic pause detection in V0.
- If realtime voice disconnects, preserve the current conversation/context and offer Retry voice or Continue with text through the existing OpenAI/FastAPI integration. If provider/server is unavailable, label Mira temporarily offline while Journal drafts and previously loaded Actions remain usable.
- For a journal voice note, transcribe first, let the person edit the transcript, then save the text. Memory starts off. The person chooses each memory item, can revoke it, and can delete it.
- Action feedback is stored separately from memory. Reusing feedback in a future Talk session requires its own explicit opt-in.
- The action catalog is a prototype set for Mpower discussion. Its fixed instructions need clinical review before use with the public.
- Provide a persistent, human-directed help option. For this demo it opens a clearly labeled placeholder: “This prototype is not connected to Mpower support. Ask the Mpower team which route belongs here.” The planned scenario is non-urgent. If the person explicitly says they are in immediate danger or asks for emergency help, stop the normal flow and show a fixed card: “This demo is not crisis support and is not connected to Mpower. Contact local emergency services or someone you trust now.” This is a demo response, not reliable crisis detection or clinical triage.

## Premises

1. The product thesis is shared context across distinct surfaces that remain independently available. A scripted loop can demonstrate continuity, but people can enter any surface and move freely.
2. The purpose is engineering exploration and a conversation with Mpower, with no monetary expectation stated for this project.
3. Core technology should be implemented for real when it makes the demo more convincing: streaming voice, consented memory, retrieval, a model/provider interface, and tool calls.
4. The demo uses a synthetic scenario and does not claim clinical effectiveness. Human escalation stays explicit and expert-defined.
5. The feature bundle alone is not distinctive. Existing products already combine voice entries, AI reflection, journaling, exercises, or personalized actions. Mira’s demo is an experiment in how continuity could fit alongside Mpower’s human support and how Mpower’s experts would shape it.

## Approaches Considered

### Approach A: Rich connected vertical slice — recommended

Build all three surfaces around one synthetic, non-urgent scenario: a young adult feels burned out, scattered, exhausted, and unable to focus. Expo Go supports fast UI/Journal/Actions iteration; the custom development build targets modern Android devices; validate the full realtime voice path on the primary physical QA/demo phone (OnePlus). Talk uses OpenAI Realtime through WebRTC. FastAPI keeps the long-lived provider key server-side and issues a short-lived session credential. A small interface wraps the one provider implementation. Journal accepts text and voice and shows an editable transcript. Each entry stays private unless the person selects, edits, and separately approves an excerpt; Talk never retrieves the full entry. Navigation is always available and consent information is inline, never a prerequisite to opening Talk. Shared-context retrieval covers only approved excerpts, current/recent action activity, and separately opted-in action ratings. Talk identifies the source it uses and continues without context when nothing relevant is available.

One FastAPI service contains explicit orchestration functions and calls bounded tools: retrieve permitted shared context, offer two fixed action IDs, and save action feedback. A small OpenAI adapter handles provider-specific session setup and event mapping; there is no separate orchestration service. The two demo actions are `task_reset_60s` (brief task reset) and `pause_60s` (60-second pause); they are neutral, non-clinical placeholders, not treatment. Mpower clinicians should later decide appropriate interventions, wording, and offering criteria. The action text and steps come from the catalog; the model may explain the options conversationally, but it does not invent an intervention. The person chooses one or declines. For a tool call, the phone relays the provider event to FastAPI with an expiring, random demo-session capability. FastAPI validates the capability, session, call ID, and arguments, runs the tool, and returns the result through the phone to the provider session. Keep the demo API on an isolated private network with a simple limit on session creation; this is not production authentication. Feedback is recorded separately; only its rating requires future-context opt-in. Navigation stays open regardless of consent choice.

Effort: 2–3 Codex days (16–24 focused Codex hours); roughly 160–480 human engineering hours by the 10–20× estimate, a throughput comparison rather than a delivery promise. Device and provider setup remain the schedule risk.  
Risk: High. Real-time audio on a phone, native build setup, and tool routing were the initial unknowns. The physical development build has since demonstrated the voice, interruption, and tool path; remaining risk is cross-surface consent/recovery verification and repeatability.  
Pros: Shows the full product thesis with real technology; creates a concrete experience for Mpower experts to critique.  
Cons: Leaves little time for visual polish and provider comparison; use one scenario and one active provider in the main path.  
Reuses: Existing Mira app and FastAPI implementation; this note records product direction, not a greenfield build assumption.

### Approach B: AI experiment bench

Keep the same three surfaces and connected demo story, while using the time to compare two model providers and test retrieval/action selection against a small sample library. Voice remains real but receives less polish.

Effort: Not part of the current build window; it adds a provider experiment after the connected experience.  
Risk: High. It is outside the approved build window and may read as separate API experiments if the shared story is not finished first.  
Pros: Directly answers your technical curiosity; produces useful questions about model behavior and retrieval for Mpower’s team.  
Cons: Divides time between experiments and experience quality; the phone demo is more brittle.  
Reuses: None.

### Approach C: Future-ready product spine

Design for a pilot with a consented memory service, clinician-reviewed action library, provider adapters, observability, robust escalation policy, and an Mpower handoff path.

Effort: Weeks of human work; days of Codex assistance.  
Risk: Low for architectural clarity, high against the current 2–3 Codex-day window.  
Pros: Clear places for clinical review and later integration; a sound path if Mpower decides to explore a pilot.  
Cons: This is too much implementation for the current demo and depends on Mpower decisions and approved content.  
Reuses: None.

## Engineering Review Decisions — 2026-10-13

- Keep one FastAPI service with explicit orchestration functions and one small OpenAI provider adapter; do not introduce a separate orchestration service.
- The API issues a random, expiring demo-session capability tied to its app-generated session ID. Require it for phone-relayed tool calls and session-scoped writes; reject expired/mismatched sessions and stale calls. Keep the API on an isolated private network, with one active session and a simple creation limit. This is a demo boundary, not production authentication.
- For WebRTC push-to-talk, set `turn_detection: null`. Press sends `input_audio_buffer.clear`; if Mira is speaking, send `response.cancel` and `output_audio_buffer.clear`; release sends `input_audio_buffer.commit` followed by `response.create`.
- If timing is recorded for the demo, measure release-to-first-audio and tool-request-to-result on the primary physical Android QA/demo phone. About three seconds from mic release to first audible response remains a provisional target, not an SLA; revisit after observing device and network behavior.
- Use focused verification only: a few backend contract checks for session expiry, memory consent/revocation, action allowlist, and feedback opt-in; one phone walkthrough; and four scripted prompt cases for boundaries/refusals. Do not add a broad UI test suite. No tests were run during the review.
