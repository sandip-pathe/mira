## Per-batch working pattern

1. Read the current feature and the accepted source; touch its visual files and only the necessary shared pieces.
2. Reuse the real native hooks, state, data and navigation. Preserve local-first behavior and the current AI/audio capabilities. Retain useful detailed features while improving presentation.
3. Report what changed and any concrete issue. Review only the affected flow; do not run a repository-wide lint/test sweep for a color/style batch. Type-check when shared types/component contracts change; avoid meaningless mirror tests.
4. Update this ledger and the decision log. Keep device-only findings pending for the user's review rather than repeatedly asking them to inspect every cosmetic update.

No EAS build per step. Font/assets/JS styling can normally be iterated through the existing development setup. If Android review shows that native system appearance needs expo-system-ui, group its addition into one later development build; no build is started while the user has it on hold.
