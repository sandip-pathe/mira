# Mira V3: Client context and mental support research

Research synthesis from the architecture discussion on 2026-11-02. This document records research and proposed future behavior; it does not replace the approved PRD or mark any proposal as implemented.

**Yes—we can build a sophisticated context system largely on the phone, with cloud workers providing the stronger language and voice intelligence.** The research supports that architecture. The harder problem is making Mira understand which information matters now, what kind of support the person wants, and when to stop using information.

I researched the engineering foundations, adaptive support research, recent clinical trials, and current ChatGPT capabilities. The design proposals below are my synthesis; the studies do not establish that Mira itself is effective. The research discussion made no implementation changes.

**Memory, retrieval, context, and support decisions need separate responsibilities.** They work together, but solving one does not solve the others.

| Component | Its responsibility | Example |
|---|---|---|
| Memory | Hold information with a source, purpose, and lifetime | “The user has a meeting tomorrow.” |
| Retrieval | Find permitted information relevant to this interaction | Retrieve the user’s approved preference for preparing one small step. |
| Context assembly | Decide what the model receives this turn | Current concern, recent exchange, meeting timing, relevant preference. |
| Support decision | Choose how to respond | Listen, ask a useful question, help prepare, or offer an activity. |
| Action lifecycle | Track what the person actually chose and did | An activity was offered, declined, started, paused, or completed. |

This distinction matters because excellent retrieval can still return an outdated concern. A fluent model can still recommend an activity at an unwelcome moment.

The [LongMemEval research](https://arxiv.org/abs/2410.10813), published at ICLR 2025, evaluates information extraction, reasoning across conversations, time, updated knowledge, and knowing when the answer is unavailable. Those are useful engineering targets for Mira. Remembering many facts is only one part of memory quality.

Anthropic’s [context engineering work](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) similarly emphasizes selecting useful information for each inference, managing accumulated history, and retrieving details when needed. For Mira, that suggests a small current understanding plus targeted retrieval, rather than replaying everything the person has ever said.

**The phone can own the personal context system.** There is no technical requirement for Mira to upload its memory database to a hosted vector service.

A reasonable division would be:

| On the phone | On the server or provider |
|---|---|
| Private Journal and saved activity work | Provider credentials and authentication |
| Approved excerpts and preferences | Strong language reasoning when requested |
| Current situation and activity state | OpenAI Realtime and Bolna voice processing |
| Search indexes and embeddings | Validation of worker requests and allowed actions |
| Permission checks, retrieval, and context selection | Usage protections and provider session management |
| Expiry, revocation, correction, and local deletion | Any provider-specific retention controls |

Expo’s SQLite documentation includes full-text search, optional vector search through `sqlite-vec`, and SQLCipher support. Some of those capabilities require native build configuration. [Expo SQLite documentation](https://docs.expo.dev/versions/latest/sdk/sqlite/)

Software Mansion’s current ExecuTorch documentation supports local text embeddings and semantic search. Its listed English embedding models include an approximately 86 MB model; multilingual choices can be considerably larger. That establishes feasibility, but the model download, memory use, indexing speed, and battery impact still need measuring on the OnePlus. [On-device text embeddings](https://docs.swmansion.com/react-native-executorch/docs/extensions/text-embeddings)

For Mira, I would design retrieval to combine:

- Permission, purpose, and expiry filters.
- Exact references such as a particular event, activity, or date.
- Keyword search for precise terms.
- Semantic search for similar meanings expressed differently.
- A relevance threshold that allows **no result**.

The model should receive a result only after those filters. A high similarity score cannot override a revoked permission or make yesterday’s situation current.

Mira already has the start of this: local SQLite, purpose-scoped retrieval, approved excerpts, and saved preferences. Its current relevance matching uses keyword overlap. Semantic retrieval would be an improvement to evaluate, rather than a complete replacement for the existing data boundaries.

**Your meeting example should become a temporary situation with an explicit lifecycle.** This is one of the strongest product ideas in the discussion.

Suppose someone says, “I’m nervous about the meeting tomorrow.”

The useful representation is: the person reported nervousness about a particular upcoming event. It should remain tied to that statement and event. It should not quietly become a permanent belief that the person is generally anxious.

My proposed behavior would be:

| What happens | How Mira’s understanding changes |
|---|---|
| The person mentions the meeting | Create temporary context for the current situation. |
| They provide a time | Attach the event time and timezone. |
| They say it moved to Friday | Replace the old timing and invalidate related assumptions. |
| They say the meeting is over | Stop treating it as an upcoming concern. |
| The known event window passes | Exclude the upcoming-meeting context from future retrieval. |
| They choose to discuss the aftermath | Use what they now say as the current situation. |
| They explicitly approve a useful general preference | Save that preference separately from the meeting. |

There are two subtleties here.

First, **an event ending does not establish that someone’s feelings have resolved**. Mira can stop preparing them for an upcoming meeting without claiming they now feel fine.

Second, if no timing was given, Mira cannot reliably know when the meeting ended. It can keep the information within the current session, or ask about timing when that changes the help it can provide. It should not ask for calendar details merely to fill a database.

Temporal memory research such as [Zep/Graphiti](https://arxiv.org/html/2501.13956v1) explicitly represents when facts are valid and when later information invalidates them. That is a useful architectural idea. Its benchmarks are engineering evidence, not evidence of clinical effectiveness, and Mira does not need to adopt the full graph platform to use the idea.

A small local database can represent event relationships, sources, validity, and expiry.

**Forgetting must cover the information derived from an event.** Deleting one row will not achieve your intended behavior if a summary, search index, or live provider session still contains the same concern.

For temporary meeting context, the lifecycle should cover:

- The situation record.
- Search entries and embeddings derived from it.
- Current summaries that mention it.
- Cached retrieval results.
- Context already loaded into an ongoing conversation.

If the person deliberately saved a Journal entry, that entry has its own retention choice. Expiring the temporary support situation should not silently delete their saved writing.

There is also a native implementation detail: Android background work is not guaranteed to execute at an exact time. The reliable rule is to check expiry whenever context is read, with cleanup performed when execution is available. An expired item must already be unusable even if physical cleanup is pending. [Android background scheduling documentation](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest)

Literal deletion requires care with indexes too. SQLite documents that ordinary FTS deletion can leave recoverable old index entries until later processing unless the relevant deletion controls are configured. [SQLite FTS5 deletion behavior](https://www.sqlite.org/fts5.html)

And local deletion cannot promise immediate removal from cloud-provider logs. OpenAI documents separate API retention controls and default abuse-monitoring retention. That boundary must be described accurately if selected context has been sent to a provider. [OpenAI API data controls](https://developers.openai.com/api/docs/guides/your-data)

**The most relevant research for “when should Mira listen or act?” is just-in-time adaptive support.** The JITAI framework considers changing needs, context, receptivity, available support options, decision rules, and outcomes. It explicitly includes providing no intervention when support would be intrusive or unwelcome. [Foundational JITAI design paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC5364076/)

That is a good starting point for the behavior you described. It does not give us a ready-made, validated algorithm for Mira.

The following is my proposed product policy:

| What the person communicates | A useful response direction |
|---|---|
| “I just need to get this out.” | Listen and reflect; leave room for more. |
| Their concern is unclear and clarification would change the help | Ask one relevant question. |
| “What should I do before the meeting?” | Help with the practical preparation they requested. |
| They want something manageable and are open to an activity | Offer one suitable activity and let them choose. |
| They decline | Respect the decision and avoid repeatedly offering it. |
| They are already doing something | Support that work instead of presenting another activity. |
| They say they are finished | Allow the interaction to end. |

Mira’s working understanding could include the current concern, what the person wants from the interaction, practical constraints, what they have tried, and any declined offer. These fields should remain tentative. Some may be unknown.

That means information gathering can happen naturally. Mira should ask because the answer would help it respond better, rather than trying to complete an assessment form in conversation.

WHO’s psychological first-aid guidance, written for human helpers after serious distressing events, emphasizes listening without pressuring disclosure, leaving room for silence, and addressing practical needs. Those communication principles are useful design references; they do not validate an AI implementation of psychological first aid. [WHO guidance](https://www.who.int/publications/i/item/9789241548205)

**There is substantial room for real AI assistance inside the environment.** Understanding language, responding personally, and adapting useful work are strong uses of the model.

For example, Mira could help a person turn a tangled thought into something they can work with, refine a message while preserving their meaning, or help them find a manageable first step. If they choose an activity, the AI can respond to the actual work in progress.

The [activity upgrade plan](PRD/mira_activity_upgrade_plan.md) already points in this direction: assistance attached to editable work, with refinements such as making something smaller, more direct, or closer to the person’s words.

The application can then enforce the dependable parts: which content is permitted, whether the user accepted, whether an activity really started, and whether context has expired. The model supplies language understanding and judgment within that structure.

I would begin with one shared conversation and activity controller. Additional specialist agents should earn their place by improving a measured problem.

**Voice, text, and calls should use the same current understanding, while their providers remain distinct.** A shared context contract could carry:

- The current situation and expressed need.
- Recent confirmed conversation.
- Relevant permitted memories.
- The chosen activity and its current stage.
- Declined suggestions.
- Source identifiers and a context revision.

Each provider adapter would turn that into the format it needs. This would help a switch from voice to text preserve the meaning of the conversation.

The Bolna boundary needs particular attention. Its documented function tools make HTTP requests to external API endpoints. They cannot directly query SQLite on the person’s phone. [Bolna function-calling documentation](https://www.bolna.ai/docs/tool-calling/introduction)

For local memory, we have two architectural choices:

- Give the call a small context snapshot at its start.
- Build an authenticated bridge that lets an available app answer a permitted context request during the call.

The snapshot is simpler and works with the current approach. A live bridge introduces background availability, timeout, revocation, and reconnection questions.

At the time of this research, Mira’s implementation gives Bolna a bounded initial snapshot, and the return-to-Talk flag does not carry a summary of what happened during the call. That means the app cannot yet honestly provide complete two-way conversational continuity across the call boundary. It needs an explicit design for what call information returns, how it is obtained, and how long it lives.

**Natural voice quality and support quality need separate evaluation.** A calm voice can make an experience easier to use, but it does not establish that Mira chose the right response.

For the voice experience, I would look at accurate microphone state, interruption, short spoken responses, tolerance for pauses, audio routing, and reliable transitions to text. For the support behavior, I would look at whether Mira understood the request, asked a worthwhile question, respected a refusal, and avoided an unwanted suggestion.

The OpenAI/MIT research on affective ChatGPT use found mixed outcomes and associations between heavier use and some poorer psychosocial outcomes. It was an early, four-week study, with important limitations; those findings do not establish that voice itself causes harm. They do reinforce the need to measure benefit beyond time spent talking. [OpenAI/MIT study](https://openai.com/index/affective-use-study/)

**The clinical evidence is promising, but it gives us a more specific ambition than “make an empathetic AI.”** These were particularly useful findings:

| Research | What it found | What it does not establish |
|---|---|---|
| **Therabot, 2025:** 210 adults; expert-developed generative chatbot versus waitlist | Greater symptom improvement in the intervention group over the study period | Superiority to a therapist or ChatGPT, or effectiveness of Mira’s design |
| **Generative AI CBT app, 2026:** 540 participants; comparison with digital CBT workbooks | Greater engagement; no demonstrated advantage on anxiety and depression outcomes | That increased use necessarily means increased benefit |
| **AI feedback in self-guided iCBT, 2026:** 1,187 participants | Better participation; no significant difference in the primary mean depression outcomes | That adding AI communication automatically improves clinical outcomes |

Sources: [Therabot trial](https://doi.org/10.1056/AIoa2400802), [AI CBT app trial](https://pmc.ncbi.nlm.nih.gov/articles/PMC12953620/), [AI feedback trial](https://pubmed.ncbi.nlm.nih.gov/41490574/).

The Therabot team also describes expert-developed training material and readiness to intervene during the trial. Its findings came from a specific system and study setting. They should not be generalized to every conversational app. [Dartmouth’s account of the research](https://home.dartmouth.edu/news/2025/03/first-therapy-chatbot-trial-yields-mental-health-benefits)

For Mira, I would initially measure whether people feel understood, obtain useful clarity, complete a self-chosen next step, and retain control over their information. Clinical outcome claims would need a separate, appropriately designed study.

**ChatGPT already covers part of this territory, so Mira needs a concrete specialization.** Current ChatGPT offerings include health-related context features, and its memory research explicitly addresses freshness and facts that change over time. We should not base Mira’s differentiation on the claim that ChatGPT cannot remember or handle dates. [Current Health documentation](https://help.openai.com/en/articles/20001036), [ChatGPT memory research](https://openai.com/index/chatgpt-memory-dreaming/)

The “Cursor for mental support” analogy becomes useful when Mira has working material and can help someone use it: a current situation, an unfinished thought, an editable message, a chosen activity, or a small step they want to take.

The differentiation I would try to establish is a combination of:

- **Support-specific timing:** listen, clarify, act, or finish in a way that fits the person’s request.
- **Useful native experiences:** work can be edited, tried, paused, and completed within the app.
- **Controlled continuity:** moving between interfaces preserves relevant understanding.
- **Temporary context by design:** an event can end without becoming part of a permanent profile.
- **Personal ownership:** approved memory remains inspectable and controllable on the phone.
- **Evidence about the experience:** decisions are reviewed and measured against realistic support journeys.

The mental-support angle becomes strong through those behaviors. The name, voice, and visual atmosphere can make them approachable, but the behaviors need to carry the product.

**There is much more that can be translated into digital support than chat, calls, and a list of activities.** Those are interfaces. The useful functions are broader:

| Function | Possible digital form |
|---|---|
| Expressing and organizing a difficult thought | Private writing, voice capture for a chosen task, editable grouping |
| Practical problem solving | Breaking a problem into manageable choices or steps |
| Preparing communication | Drafting, rewriting, and rehearsal |
| Learning and practising skills | Guided experiences with pacing and feedback |
| Supporting everyday routines | User-chosen plans and check-ins |
| Remembering what was useful | Explicitly approved preferences |
| Connecting with people | User-directed preparation for outreach or professional appointments |
| Supporting ongoing care | Structured material shared by the person with a care team, if that becomes the product’s scope |
| Creating a comfortable interaction | Optional sound, movement, tactile cues, and low-demand ways to participate |

There is evidence for digital programs that do more than conversation. WHO’s Step-by-Step combines structured self-help techniques with brief human support. A randomized trial in Lebanon reported improvements in symptoms and functioning, while noting uncertainty from high attrition. [Step-by-Step trial](https://pubmed.ncbi.nlm.nih.gov/35577536/)

A randomized trial involving 1,711 people found benefits from a digital CBT-for-insomnia program compared with sleep-hygiene education. That supports researching structured digital sleep programs; it does not transfer those results to a short relaxation screen or sleep soundscape. [Digital insomnia trial](https://pmc.ncbi.nlm.nih.gov/articles/PMC6583463/)

AI can also support human relationships. The HAILEY trial with 300 peer supporters found improved expressed empathy when AI helped them compose responses. It measured communication quality, not clinical recovery. [HAILEY research](https://www.nature.com/articles/s42256-022-00593-2)

More specialized digital interventions include virtual-reality programs such as gameChange. Their evidence applies to defined populations, protocols, and outcomes. They show the breadth of what can become digital, while also showing why each new capability needs its own rationale. [gameChange trial](https://www.thelancet.com/article/S2215036622000608/pdf)

For Mira, sensory design could make an activity comfortable and accessible. I would treat therapeutic claims about haptics, colors, or sound as separate questions requiring evidence.

Passive sensing is another research area, but I would approach it carefully. A recent review found major variation in devices, methods, reporting, and validation across digital-phenotyping studies. A phone or wearable signal should not become an unquestioned statement about someone’s emotional state. [Digital phenotyping review](https://pmc.ncbi.nlm.nih.gov/articles/PMC13391508/)

**The next design work should make the desired behavior concrete before choosing more infrastructure.** I would develop four artifacts from this research:

1. **A memory lifecycle specification:** what is temporary, what may persist with approval, how events expire, and what “forget” removes.
2. **A set of support conversations:** examples where listening, asking, practical help, an activity, or ending the interaction is appropriate.
3. **A shared context contract:** what text, Realtime, Bolna, and Activities can read and update.
4. **An evaluation set of full journeys:** rescheduled meetings, declined activities, voice-to-text changes, call returns, revoked excerpts, and situations where Mira should say it does not know.

For that evaluation, I would measure stale-context use, incorrect remembered facts, unnecessary questions, unwanted suggestions, refusal handling, and successful context transitions alongside user-reported usefulness. The [APA app evaluation model](https://www.psychiatry.org/psychiatrists/practice/mental-health-apps/the-app-evaluation-model/) is a useful additional lens because it considers access, privacy, clinical foundation, usability, and the person’s goals together.

The first concrete journey I would design is yours: someone arrives nervous about a meeting, chooses the kind of help they want, uses whichever interface suits them, and can let the situation—and its temporary memory—end.
